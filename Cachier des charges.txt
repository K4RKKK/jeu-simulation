# CAHIER DES CHARGES — V1

# Simulation de civilisation émergente préhistorique

### Three.js / TypeScript / Monde procédural persistant

---

# 1. VISION DU PROJET

Créer un jeu de simulation de vie et de civilisation entièrement systémique dans lequel une petite population humaine apparaît dans un monde sauvage, sans technologie avancée, sans connaissances artificiellement données au joueur et sans arbre technologique classique.

Le joueur n'incarne pas directement un personnage.

Il observe une population vivre, survivre, apprendre, échouer, transmettre ses connaissances et progressivement construire une civilisation.

Les personnages doivent pouvoir :

* avoir faim ;
* avoir soif ;
* boire de l'eau contaminée ;
* tomber malades ;
* s'empoisonner ;
* être blessés ;
* saigner ;
* souffrir ;
* mourir ;
* dormir ;
* avoir chaud ou froid ;
* explorer ;
* ramasser des ressources ;
* transporter des objets ;
* expérimenter ;
* apprendre ;
* oublier certaines informations ;
* transmettre leurs connaissances ;
* fabriquer des objets ;
* découvrir de nouvelles techniques ;
* construire ;
* développer des relations ;
* s'attacher ;
* se méfier ;
* se disputer ;
* coopérer ;
* former des groupes ;
* communiquer ;
* progressivement développer un vocabulaire commun ;
* enseigner ;
* observer les autres ;
* développer des compétences différentes.

Le monde doit pouvoir continuer à évoluer **24 heures sur 24**, même lorsqu'aucun joueur n'est connecté.

Le jeu doit être construit comme une véritable simulation émergente.

Il ne doit PAS fonctionner comme :

> Niveau 3 atteint → découverte du feu.

Il doit fonctionner comme :

> Un individu connaît certaines propriétés du bois.
> Il sait manipuler des branches.
> Il a observé de la chaleur ou des étincelles.
> Il expérimente plusieurs fois.
> Certaines expériences échouent.
> Une combinaison correcte de matériaux, conditions et gestes peut produire une braise.
> Il doit ensuite comprendre comment maintenir cette braise.
> Après plusieurs expériences réussies, cette connaissance devient suffisamment fiable pour être reproduite et enseignée.

La philosophie générale est :

**Simulation → émergence → observation → transmission → civilisation.**

# 2. DIRECTION ARTISTIQUE

Le projet doit utiliser une direction artistique :

* low-poly ;
* polygon ;
* stylized ;
* très lisible ;
* formes simples ;
* personnages arrondis ;
* proportions légèrement cartoon ;
* environnement minimaliste mais joli ;
* textures simples ;
* matériaux colorés ;
* silhouettes facilement reconnaissables.

Les personnages doivent évoquer l'esprit de personnages très simples et arrondis comme ceux que l'on peut voir dans certains jeux stylisés modernes, sans reproduire exactement un personnage ou une identité visuelle existante.

Pour la V1 :

* tête sphérique ou légèrement déformée ;
* torse simple ;
* bras et jambes arrondis ;
* mains simplifiées ;
* animations minimalistes ;
* couleurs permettant de distinguer les individus.

Pas besoin de personnages AAA.

La priorité absolue est :

**lisibilité + performance + capacité d'afficher beaucoup d'individus.**

---

# 3. CAMÉRA

Vue principale :

**vue du dessus 3D légèrement inclinée.**

La caméra doit permettre :

* déplacement WASD ;
* déplacement souris bord d'écran optionnel ;
* zoom molette ;
* rotation ;
* déplacement rapide ;
* zoom très éloigné ;
* zoom proche d'un individu ;
* centrage automatique sur un personnage sélectionné.

À grande distance :

* afficher principalement le monde ;
* simplifier fortement les personnages ;
* masquer les petits objets inutiles.

À courte distance :

* afficher les personnages ;
* équipements ;
* objets ;
* animations ;
* informations contextuelles.

# 4. PRINCIPE FONDAMENTAL D'ARCHITECTURE

Ne PAS placer la logique principale de simulation directement dans les objets Three.js.

La simulation et le rendu doivent être totalement séparés.

Architecture :

```text
SIMULATION
↓
état logique du monde
↓
snapshots / événements / deltas
↓
CLIENT THREE.JS
↓
visualisation
```

Three.js ne doit jamais décider :

* si quelqu'un a faim ;
* où quelqu'un décide d'aller ;
* si quelqu'un apprend ;
* si une maladie progresse ;
* si un objet est fabriqué ;
* si quelqu'un meurt.

Three.js ne fait qu'afficher les résultats.

# 6. MONDE 24H/24

Le monde ne doit PAS dépendre du navigateur.

Le serveur possède le monde.

Le navigateur est uniquement un observateur.

Ainsi :

```text
Serveur actif
↓
simulation active
↓
personnages continuent de vivre
↓
joueur déconnecté
↓
simulation continue
↓
joueur revient
↓
client récupère le nouvel état
```

Cela permettra plus tard :

* hébergement permanent ;
* serveur personnel ;
* mondes publics ;
* plusieurs observateurs ;
* historique complet d'une civilisation.

Pour le développement local, le serveur pourra naturellement fonctionner sur le PC.

# 7. HORLOGE DE SIMULATION

Créer une horloge indépendante du framerate graphique.

Exemple :

```ts
SimulationClock
gameTime
deltaGameMinutes
timeScale
day
season
year
```

Le temps de jeu doit être configurable.

Ne jamais hardcoder une correspondance définitive entre temps réel et temps simulé.

Exemple :

```ts
TIME_SCALE = 24;
```

Le moteur doit pouvoir fonctionner :

```text
x1
x2
x4
x8
x16
x32
```

dans les environnements de développement.

Le temps persistant du serveur utilise une vitesse configurable définie pour le monde.

# 8. TICK DE SIMULATION

Ne jamais exécuter toute l'intelligence de tous les personnages à chaque frame.

Créer plusieurs fréquences.

Exemple :

### Tick rapide

250 ms

Pour :

* mouvements ;
* combats ;
* actions courantes.

### Tick moyen

1 seconde

Pour :

* besoins ;
* décisions ;
* perception.

### Tick lent

5 à 30 secondes

Pour :

* maladies ;
* relations ;
* connaissances ;
* environnement ;
* croissance ;
* régénération.

### Tick très lent

Pour :

* vieillissement ;
* saisons ;
* modifications environnementales lentes.

Le système doit être configurable.

# 9. MONDE PROCÉDURAL

Chaque monde possède :

```ts
worldSeed: string
```

Une même seed doit générer le même monde initial.

Le monde doit être découpé en chunks.

Exemple :

```text
64 m × 64 m
```

par chunk.

Ne jamais générer toute une carte gigantesque en permanence.

# 12. HYDROLOGIE

V1 :

* rivières ;
* petits lacs ;
* étangs ;
* éventuellement source d'eau.

Chaque source possède des propriétés.

```ts
WaterSource {
    volume
    contamination
    turbidity
    pathogenLoad
    temperature
}
```

Boire de l'eau ne doit pas automatiquement hydrater sans conséquence.

Exemple :

```text
Eau claire visuellement
≠
Eau forcément potable
```

Une rivière peut être moins dangereuse qu'un étang stagnant.

Un cadavre ou certaines activités proches d'une eau pourront plus tard augmenter sa contamination.

```text

↓

↓

↓
mort
```

Ne jamais tuer immédiatement un personnage parce qu'une barre atteint zéro.

# 27. MORT


# 28. SYSTÈME DE PERCEPTION

Les personnages ne sont PAS omniscients.

Ils connaissent uniquement :

* ce qu'ils voient ;
* ce qu'ils entendent éventuellement ;
* ce qu'ils se rappellent ;
* ce qu'on leur transmet.

Créer :

```ts
PerceptionSystem
```

avec :

```text
visionRange
fieldOfView
visibility
```

Un personnage situé à l'autre bout de la carte ne doit pas savoir qu'un arbre a été coupé.

# 30. INTELLIGENCE ARTIFICIELLE

L'IA doit utiliser une architecture hybride :

### Utility AI

Décide **quoi faire**.

### Planner

Décide **comment le faire**.

Exemple :

```text
Hydratation critique
↓
utility boire = 0.97

faim = 0.42
fatigue = 0.21

Décision : boire
```

Ensuite :

```text
trouver source connue
↓
se déplacer
↓
atteindre l'eau
↓
boire
```

# 39. DÉCOUVERTE

Ne jamais faire :

```ts
if (random() < 0.01)
    unlockFire()
```

Les inventions doivent nécessiter une combinaison de facteurs.

Exemple simplifié :

```text
connaissance bois
+
matériau sec
+
expérience friction/percussion
+
curiosité
+
temps disponible
+
expérimentation
```

peut éventuellement produire :

```text
chaleur
↓
fumée
↓
braise
```

Puis l'individu doit comprendre comment :

```text
nourrir la braise
+
protéger la braise
+
ajouter du combustible
```

avant de maîtriser réellement le feu.

---

# 40. FEU

La maîtrise du feu doit être un accomplissement majeur.

Étapes possibles :

```text
1. connaissance matériaux secs
2. observation chaleur
3. expérimentation
4. génération d'une braise
5. maintien de la braise
6. ajout combustible
7. feu stable
8. reproduction volontaire
9. transmission
```

Il doit être tout à fait possible qu'une population passe longtemps sans réussir à fabriquer volontairement du feu.

---

# 41. EXPÉRIMENTATION

Créer :

```ts

```

Un personnage curieux peut expérimenter lorsqu'il :

* n'est pas en danger ;
* n'a pas de besoin critique ;
* possède des matériaux ;
* possède certains concepts.

Les essais peuvent :

```text

donner une observation

créer une nouvelle hypothèse
```

Les échecs doivent être utiles.

# 42. TRANSMISSION DU SAVOIR

* sexe ;
* fertilité ;
* couple/relation suffisamment stable ;
* grossesse ;
* naissance ;
* enfant dépendant.

Le système doit surtout être conçu de façon extensible.

# 111. DEFINITION OF DONE — V1

La V1 est considérée terminée lorsque l'on peut :

1. créer un nouveau monde à partir d'une seed ;

2. générer automatiquement une carte cohérente contenant terrain, eau, arbres, pierres et nourriture ;

3. faire apparaître une petite population ;

4. observer les individus vivre sans intervention du joueur ;

5. voir chaque individu posséder ses propres besoins ;

# 114. RÈGLE ABSOLUE DU PROJET

Avant de développer une nouvelle fonctionnalité, toujours se demander :

# 115. INSTRUCTION FINALE POUR CLAUDE OPUS

Tu dois construire ce projet comme un moteur de simulation extensible et non comme une succession de scripts.

Priorités absolues :

```text
1. architecture
2. déterminisme
3. séparation simulation/rendu
4. autonomie des individus
5. connaissances individuelles
6. comportements causaux
7. émergence
8. performances
9. observabilité
10. graphismes
```

Ne jamais sacrifier l'architecture de la simulation pour obtenir rapidement une démonstration visuelle.

Commencer par une version extrêmement simple graphiquement mais possédant une base simulation propre.

Chaque système doit pouvoir être testé sans Three.js.

La commande de simulation headless doit rester fonctionnelle pendant tout le développement.

À la fin de chaque phase :

```text
compiler
lancer les tests
lancer simulation headless
vérifier erreurs runtime
vérifier performances
documenter les changements
```

Ne pas commencer plusieurs systèmes incomplets simultanément.

Terminer et tester chaque fondation avant de construire la suivante.

L'objectif de cette V1 n'est pas encore d'avoir une civilisation moderne.

L'objectif est d'obtenir **un petit groupe d'humains virtuels suffisamment autonomes pour que l'on puisse les observer et voir apparaître des comportements et des histoires que nous n'avons pas explicitement scriptés.**

C'est cette architecture qui permettra ensuite au projet de devenir une simulation extrêmement profonde.
